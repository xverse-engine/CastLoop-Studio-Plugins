# CastLoop 小游戏生成与平台接入 1.2

## 任务路由与正式接入边界

- 自然语言创作／对话修改：先读 [自然语言创作](references/common/自然语言创作.md)。作者不必自备技术稿，Agent 负责形成玩法草稿。
- 创作端生成任务／可复用小游戏资产：读 [创作端生成与资产复用](references/common/创作端生成与资产复用.md)。同时交付 H5、完整 `miniGameData`、`displayName` 和 `editorSchema`；开发部署读 [Skill Runner 接口](references/common/Skill-Runner接口.md)。创作者不用写 JSON，生成成功后由平台加入项目素材库，其他节点可选择并单独调整关键参数。
- 玩法、视觉生成：沿用下文流程与 [全局 UI](references/common/全局UI.md)、[素材](references/common/素材与九宫格.md)。本 Skill 不是任意玩法零代码解释器，选定玩法仍需独立引擎与视图。
- 正式平台接入：读 [宿主协议](references/common/宿主协议.md)、[商业与权益](references/common/商业与权益.md)、[存档与发布](references/common/存档与发布.md)，类型参考 [host-api.d.ts](assets/host-contract/host-api.d.ts)。注册的密码锁与二合炼药已提供宿主接入代码；本地代码接入不等于线上部署或三端认证。新增游戏或权益必须先完成注册与相关测试。
- 发布包：使用 `game-package.json` 与 `scripts/assemble-runtime.mjs`。第二个参数是当前故事的资产根目录，脚本自动输出到 `mini-games/<gameId>/<gameVersion>/`。保留的 `assemble.mjs`、示例工程和 `preview` 仅是 1.0 兼容预览。

所有小游戏图片资产的最终格式统一为 **WebP**，包括背景、面板、九宫格切片、物件、图标与图集；保留透明通道与原显示尺寸，不能只改后缀。生成原稿可用 PNG 等格式留在私有工作区，运行包及实际加载引用必须使用转换后的 WebP。每个小游戏在故事资产下有独立的 `mini-games/<gameId>/` 文件夹，代码、配置、图片、字体与音视频均随固定版本放入其子目录；多个小游戏不能平铺混放或引用另一个游戏目录内的私有资源。详见 [素材](references/common/素材与九宫格.md) 与 [存档与发布](references/common/存档与发布.md)。

玩法通过 `ctx.host` 请求平台能力。真实价格、钻石、会员资格、广告奖励和权益由服务端决定；游戏不持有账户令牌，不直接接收银台或广告 SDK。预览 Mock 与正式宿主必须显式区分，正式握手失败不回退模拟成功。

不编写或维护工作日志。按任务需要输出交付清单和定向验证结果；除用户特别要求，只运行修改相关模块测试。未授权不提交、推送、发布或安装到全局 Skill 目录。

从作者描述及授权上下文明确故事、玩法、宿主能力；已有结构稿时沿用，没有结构稿时由 Agent 整理，不要求作者补技术文档或 JSON。用 [输入模板](references/templates/项目输入.md) 记录已确认项和影响玩法的缺项。已有可执行玩法优先复用。新增玩法先定义输入、状态、判定和可替换的程序接口，再生成 UI。日常新增或替换玩法见 [玩法迭代操作指南](references/common/玩法迭代操作指南.md)。

## 新增玩法与生成故事预览是两个任务

**新增玩法**：用户只提交 UI 框架和玩法文档时，将资料归档为独立玩法包。以目标玩法库判断是否已有该玩法，参考工程中的同名示例不算。以用户指定名称选稳定 ID，在 `references/gameplay/<id>/` 存放 `inputs/ui/`、`inputs/rules/`、`inputs/sources.json` 和 `玩法定义.md`。本地文件保留原名，链接记录原 URL。定义需列出页面、状态、触发及去向、输入、判定、资源槽位和可独立测试的逻辑；有明确实现要求时可提供独立引擎与测试。已有同 ID 时保留原包，只有明确指定替换才更新原玩法。未给故事资料时，到玩法包为止，不创建故事项目，不改故事项目的注册或资源清单，不生成主题 UI、素材或 HTML 预览。

**生成故事预览**：用户提供故事信息并要求生成时，读取指定玩法包及故事输入。用 `node scripts/intake-game.mjs "<工作项目>" "<玩法ID>" "<UI 文件或 HTTPS 链接>" "<玩法文档或 HTTPS 链接>"` 将输入归档到工作项目的 `games/<id>/inputs/`。在目标项目实现视图并按需更新 `games/registry.mjs`、`project.json`，按下面的通用工作流生成独立预览。

## 参数、权益和章节隔离（1.2）

- Runtime 在 `miniGameData: {}` 内存储和传递玩法参数，不把每种小游戏字段展开为故事顶层字段。H5 自行解析自己声明的 schemaVersion；缺失或不支持的参数报错，不偷偷进入关卡 1。二合炼药使用 mode=story_single_level、levelId=1..10，通关当前关卡即回故事。
- 创作任务按 `parameterMode=generate_from_description` 从描述生成参数和关键参数表单；逐字段优先级为 API 显式覆盖（含 0/false）> 描述指定值 > Skill 默认值。`editorSchema` 仅声明允许编辑的标量字段，不包含运行代码或任意 HTML。同一素材可被多个节点引用，节点各自克隆参数；改节点参数不改原包、不串改其他节点、不重新生成游戏。
- 默认 diamondCost=10、freeUses=1、membership=true、rewardedAd=true。仅对未指定字段补默认；作者显式指定 0 或 false 必须保留。逐字段优先级为节点单项配置 > 节点统一配置 > 游戏单项配置 > 游戏统一配置 > 平台默认。配置必须经过发布服务校验，价格不得由 H5 请求决定。
- 免费额度和已购权益按账号/storyId/nodeId/interactionId/gameId/grantKey 隔离。runId、会话重建、版本升级和重复打开不能重新赠送免费次数；不同章节同款游戏独立计算。
- 购买与使用分开：已购未使用权益保存在平台；先预留一次使用，再把执行后的快照与次数消耗原子提交。关闭、断网、崩溃后查询原操作和权威存档，不重复扣钻或扣次数。
- 打开时传入 showRewardedAd 和各 offer.methods.available；页面按真实可用性显示广告入口，能力变化后刷新，点击前再次确认。不能只因配置 rewardedAd=true 就展示可用广告，更不能用定时器伪造观看成功。
- 用 [1.2 接入示例](references/templates/merge-node.example.json) 和 [宿主类型](assets/host-contract/host-api.d.ts) 生成调用。小游戏只能请求获取权益；支付方式选择、账号、会员、广告任务和结算回执留在宿主。新玩法的 grantKey/kind/effect 属于注册元数据，平台管理通用余额与消费，H5 实现实际效果，不要求作者单独部署后端。

## 故事触发与宿主恢复

小游戏可像拼纸一样在节点视频的任意秒作为过程互动触发，也可用节点完成出口。不要在 H5 内自行计时判断故事触发点，宿主根据 `triggerAtMs` 或 `anchor: {type: "video_time", sectionId, variantId, atMs}` 暂停视频并打开游戏；发布格式二者互斥，正文视频用稳定锚点，时间不放入 miniGameData。过程小游戏成功或授权跳过后继续当前视频；未配置失败目标时失败也继续，配置时走失败目标。节点完成出口保持成功/失败目标路由。退出不伪造通关，存档与权益隔离不变。

参考 [视频中途触发示例](references/templates/timed-mini-game-node.example.json)。创作端新增入口目前仅 SIT 展示，这只是前端 rollout，不限制后端保存/发布/权益接口或消费端运行。不要把 SIT 判断复制进 H5 包或服务端。

## 通用工作流

1. 读 [全局 UI](references/common/全局UI.md) 和 [验收](references/common/生成与验收.md)，只读本任务选中的 [玩法定义](references/gameplay/)。
2. 从故事资料提取场景、情绪、物件与指定主色、字体。先按 [素材与九宫格](references/common/素材与九宫格.md) 建立素材清单，再实际调用生图能力生成**场景、面板原图和玩法物件图**。先把故事指定色同步到各档主题配置、素材提示词和运行时颜色变量，检查所有故事 UI 的状态和层级，禁止把固定彩色写进 CSS、HTML 内联样式、脚本绘制或图标。使用 audit-theme-colors.mjs 并做至少两种输入色板的浏览器回归。先区分素材角色：页面背景（scene）按 9:16 竖幅生成，以等比 cover 适配约 375×812 的手机容器；跨横竖比例复用的面板原图（panel）才优先近方形，中心底纹等比覆盖。两种素材分别生成与映射。每档必须先自动去底并复核真实外轮廓，再用 prepare-panel.py 裁掉透明留白；只有裁后的面板才可切为连续对齐的 3×3 网格，四边单次绘制，禁止重复平铺；按目标 DPR（至少验 2× 与 3×）核对角片与边条像素密度；面板外沿和物件必须有真实透明通道，面板容器和叠色不得填黑露底；用于信息区、操作区和相应弹层，把各级物件图接入棋盘和目标。代码绘制的框体、色块、渐变、Emoji 和字符图标仅可用于临时缺图回退。若生图不可用，明确标记交付未完成及缺失项。三档用于视觉对比时，场景构图、面板材质和装饰密度都要可区分。
3. 按结构稿实现页面和状态。返回、重开、帮助等无底功能图标保留透明热区，通过轻量字形投影增强对比。Merge-2 新局直接显示「目标＋开始」弹窗，点击一次开始即进入棋盘。遵循 [玩法接入契约](references/common/玩法接入.md)，让玩法负责判定，主题负责视觉，宿主负责广告、支付与剧情导航。现成系统组件从源设计或宿主复用。
4. 在独立工作项目准备图片，完成去底、裁边和九切后将全部运行时图片转换为 WebP，同步更新图片引用、主题与素材映射，复核透明、尺寸和切片像素。再运行 `node scripts/audit-runtime.mjs <项目目录>` 和 `node scripts/assemble-runtime.mjs <项目目录> <故事资产根目录>`，为每个游戏生成独立版本包与文件哈希；只要求目标游戏版本目录为空，不要求清空整个故事资产目录。旧 1.0 示例才使用 `audit-art-alpha.py` 与 `assemble.mjs --require-art`，其产物不能当作符合新资源规则的发布包。按验收检查实际加载的图和字形。玩家区每种语言所有可见文本使用故事指定字体映射，覆盖按钮、数字、提示和弹窗；实际发生字体回退时修正后再交付。输出输入、素材、运行时、验证记录。

案例的故事名、颜色、字体选型、文案、素材、关卡及计费值是该案例输入。复用时以新输入为准。评审意见覆盖旧稿时记录对应决定；未定义的关卡和页面列为待确认。
